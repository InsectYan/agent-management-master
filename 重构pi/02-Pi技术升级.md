# 02 — Pi 技术升级

升级范围只在 `app/lib/schemes/pi/` 和它的依赖。Egg、其它 scheme、OpenTelemetry 本轮不动。

---

## 1. 依赖

三个 Pi 包同一版本，一次换完。不要只升其中一个。

| 包 | 现在 | 目标 |
|----|------|------|
| `@earendil-works/pi-coding-agent` | `^0.77.0` | `^1.1.0` |
| `@earendil-works/pi-agent-core` | `^0.77.0` | `^1.1.0` |
| `@earendil-works/pi-ai` | `^0.77.0` | `^1.1.0` |
| `jsonrepair` | `^3.12.0` | `^3.15.0` |

`package.json` 的 `engines.node` 改为 `>=22.19`。本地和 CI 用 22。Docker 已经是 `node:22-alpine`，镜像不用为这次改标签。

`AgentHarness`（agent-core 的耐久 lane）不接入。HTTP 入口仍是一次请求一轮 `createAgentSession`。

---

## 2. 会话入口

`piRunTurn.mjs` 继续作为完整引擎。`runTurn.js` 的轻量回退保留，只在下面两种情况使用：

- `PI_LIGHTWEIGHT=1` 或 `PI_ENGINE=light`
- 完整引擎加载失败

回退时 outbox 字段与完整引擎相同，响应形状不变。生产默认走完整引擎。

完整引擎接入 Pi 已有能力，不平行再写一套：

| 能力 | 本仓动作 |
|------|----------|
| `createAgentSession` · `SessionManager` · `ModelRegistry` | 继续作为一轮的入口。密钥仍来自 `resolveLlm()`，经现有 `AuthStorage.inMemory` 注入 |
| `DefaultResourceLoader` | 人设和 `SKILL.md` 的路径指向插件目录，见第 3 节 |
| `defineTool` | 业务工具由插件登记后装进当次会话 |
| `session.compact` 与 `session.jsonl` | 短期对话以 Pi 会话为准。本仓只做压缩后截断和失败兜底 |
| Extension（动态上下文、`tool_call`） | 需要时由插件登记上下文提供器。Pi 方案不写死某个业务的事实 |

一轮的对外结果保持现在的返回：

```text
{ reply, outbox, workspace, session_dir, pi_engine }
```

`pi_engine` 为 `pi-coding-agent` 或 `light`。`PiExecutor` 放进 `output` 的字段不增删：`reply`、`message_type`、`intent`、`session_id`、`scheme`、`outbox`、`workspace`、`session_dir`、`llm_profile_id`。

## 3. 资源从插件目录读

现在 `initSkillWorkspace` 会把 `SKILL.md` 拷到工作区，并在没有 `AGENTS.md` 时写一份。升级后停止这两步。

加载器读取：

| 文件 | 路径 |
|------|------|
| 人设 | `plugins/<skill>/prompts/AGENTS.md`，可选 `SOUL.md`、`APPEND_SYSTEM.md` |
| 场景说明 | `plugins/<skill>/SKILL.md`；多场景时再加 `plugins/<skill>/scenes/<scene>/SKILL.md` |
| 业务工具 | `plugins/<skill>/tools/` 的登记，不把目录拷进工作区 |

`note-skill` 今天没有 `prompts/`。批次 4 补一份与现文案等价的 `AGENTS.md`，内容来自现在写进工作区的那段用途说明，不改对用户可见的路由和落库。

工作区只保留运行时数据：

```text
{WORKSPACES_ROOT}/{projectId}/skill_{skillName}/
├── {sessionId}.jsonl
└── sessions/{sessionId}/
    ├── inbox.md
    ├── context.json
    └── outbox.json
```

`inbox.md` 仍是本轮输入，由执行器写入。它不是技能文案的第二份真相。

旧路径 `{WORKSPACES_ROOT}/skill_{skillName}/` 在批次 3 结束前仍能被读到。新会话写到带 `projectId` 的路径。批次 5 之后不再读旧路径。

## 4. 短期记忆

新建 `app/lib/schemes/pi/memory/short.js`，只做三件事：

1. 打开或创建该会话的 `session.jsonl`（路径见上）。
2. Pi `session.compact` 成功后，按 `firstKeptEntryId` 截断 jsonl。
3. 连续压缩失败时，把当前 jsonl 改名为带时间的归档，再开一份新会话文件。归档留在同一会话目录，不另建库。

不在这里做向量、不在这里合并 `MEMORY.md`。长期记忆仍走 `MemoryEngine`，见 [04](./04-项目隔离-记忆与知识库.md)。

## 5. 工具

| 层 | 放哪 | 例子 |
|----|------|------|
| 通用 | `app/lib/schemes/pi/tools/` | 只读查本项目知识库。默认不启用，技能在 `config.pi.tools` 里点名才装上 |
| 业务 | `plugins/<skill>/tools/` | 和该技能出参、入参绑在一起的工具。`note-skill` 本轮可以没有 |

注册发生在开会话时：通用工具 ∪ 该技能登记的工具。未登记则只有 Pi 自带的 `read` / `grep` / `bash` / `write`，与现在 `note-skill` 的工具集一致。

`bash` 的工作目录仍是该技能的工作区，不能落到别的项目目录。

## 6. 模型与环境变量

继续读现有名字，运维切换模型不用改协议：

- `LLM_DEFAULT_PROFILE`
- `LLM_PROVIDER`
- `LLM_MODEL` / 现有 `OLLAMA_*`
- 请求里的 `llm_profile` 仍优先于技能默认，再优先于平台默认

`PI_LIGHTWEIGHT`、`PI_ENGINE` 保留。

`1.1.0` 的 `createAgentSession`、`DefaultResourceLoader`、`SessionManager.open/create`、`defineTool` 以安装后的包导出为准。若与 `0.77` 的调用参数不一致，只改 `piRunTurn.mjs` 的接入，不在外面再包一层自研会话。

完成标准见 [05](./05-分批节奏.md) 批次 3 和 [06](./06-验证方案.md) 的升级冒烟。
