# 06 — 验证方案

验证分两层。

- **自动：** 不依赖真实模型。放进 `npm test` 或现有 selftest。批次 6 前，每批至少跑和该批相关的条目。
- **手动：** 需要本地模型。不放进默认 `npm test`。升级 Pi 包的那一批做一次，结果记在本文件末尾的记录表。

不在本轮做黄金集、多模型打分、自动改写 `SKILL.md`。

---

## 1. 契约（必须自动）

对照 `docs/api/README.md` 与 [README](./README.md) 冻结表。

| 编号 | 做法 | 通过 |
|------|------|------|
| C1 | `GET /health`、`GET /ready` | 200 |
| C2 | `GET /api/plugins` | 200。每条仍有 `name`、`scheme`。多出来的 `project` 不替代这两个字段 |
| C3 | `GET /api/plugins/note-skill` | `scheme` 为 `pi`，`project` 为 `platform` |
| C4 | `GET /api/projects` | `count === 5`。五个 id：`platform`、`novel`、`fitness`、`ops`、`testgen`。每个 id 下的 skill 名与 `config/projects.json` 里已加载的名字一致 |
| C5 | `POST /api/skills/note/chat`，body `{ "action": "list", "session_id": "default" }` | 200。响应含 `reply`、`output`、`meta`、`skill=note-skill`、`scheme=pi`。不要求模型 |
| C6 | `GET /api/memory`、`GET/POST /api/memory/note-skill` | 与现有 `test/app/controller/memory.test.js`、`scripts/selftest-memory.js` 一致 |
| C7 | 响应里不出现 apiKey、`DATABASE_URL` | 对 C5、C6 的 JSON 做字符串检查 |

现有用例能覆盖的，扩展断言，不复制第二套请求。

## 2. 项目隔离（必须自动）

用临时目录，不读开发者本机的 `memory_files`。

| 编号 | 做法 | 通过 |
|------|------|------|
| I1 | 只在 `memory_files/platform/note-skill/MEMORY.md` 写入标记 `PLATFORM_ONLY`。以 `note-skill` 读取 | 内容含该标记 |
| I2 | 再在 `memory_files/testgen/testgen-skill/` 写入 `TESTGEN_ONLY`。仍以 `note-skill` 读取和搜索 | 结果不含 `TESTGEN_ONLY` |
| I3 | 向量：向 `research_memory` 插入一行 `project_id=platform`，向 `testgen_memory` 插入一行 `project_id=testgen`，搜索 `research-skill` | 只返回 platform 行 |
| I4 | 知识库：`knowledge/platform/a.md` 与 `knowledge/testgen/a.md` 各写不同正文。以 platform 调用 `read('a.md')`，再尝试 `read('../testgen/a.md')` | 第一次只看到 platform 正文。第二次失败，不返回 testgen 正文 |
| I5 | 登记表把 `note-skill` 写成两个项目，启动加载 | 进程拒绝启动或拒绝加载该技能，日志能看出冲突 |
| I6 | 某个 skill 的 `project` 写成 `unknown` | 该技能不在 `/api/plugins` 里 |

I3 在没有 Postgres 时走现有 SQLite 关键词后端，断言同样是「搜不到另一个项目的文本」。

## 3. 旧路径迁移（批次 2 必须自动，批次 5 改为否定断言）

| 编号 | 何时 | 做法 | 通过 |
|------|------|------|------|
| M1 | 批次 2 至 4 | 只有 `memory_files/note-skill/MEMORY.md`，内容为 `OLD_NOTE`。`GET /api/memory/note-skill` | 响应含 `OLD_NOTE`，且新路径文件已出现 |
| M2 | 批次 2 起 | 对新路径 `append` 一段 `NEW_NOTE` | 新路径含 `NEW_NOTE`。旧文件不再被写入 |
| M3 | 批次 5 | 代码与测试不再打开 `memory_files/{skillName}/MEMORY.md` 这种少一层项目的路径 | 检索为 0。M1 删除或改成「只读新路径」 |

## 4. Pi 行为（list 自动，完整引擎手动）

| 编号 | 自动/手动 | 做法 | 通过 |
|------|-----------|------|------|
| P1 | 自动 | `PI_ENGINE=light`，`note-skill` chat，消息任意，无密钥也可 | `output.outbox` 含 `reply`、`message_type`、`intent`、`agent_name`。`scheme` 为 `pi` |
| P2 | 自动 | `action=list` | 不创建 `outbox.json`，响应里没有 `pi_engine: pi-coding-agent` 的模型调用痕迹（可用现有短路分支断言 `output.action === 'list'`） |
| P3 | 自动 | 批次 4 之后跑一次 light chat | 该会话工作区在 `workspaces/platform/skill_note-skill/` 下，目录内没有新生成的 `SKILL.md`、`AGENTS.md`、`MEMORY.md` |
| P4 | 手动 | 配置好现有 Ollama 或其它 `llm_profile`，`POST /api/skills/note/chat`，消息「记住我喜欢简短回复」 | `pi_engine` 为 `pi-coding-agent`。随后 `GET /api/memory/note-skill` 能看到合并结果，或响应 `meta.memory_ops_applied` ≥ 0 且请求 200。outbox 四字段齐全 |
| P5 | 手动 | `POST /api/skills/note/chat/stream` | 事件顺序里出现 `status` 与 `done`。`done` 的 JSON 含 C5 那组字段 |
| P6 | 手动 | 同一 `session_id` 再发一轮 | 第二轮仍 200。`session.jsonl` 仍在该项目工作区，不写到 `workspaces/skill_note-skill/` |

P4 不要求固定措辞。断言字段和「记忆接口仍可用」，不断言模型原句。

## 5. 业务回归（必须自动的部分）

这些技能不改 scheme。批次 1 之后确认它们仍被加载，且 `project` 正确。

| skill | project | 检查 |
|-------|---------|------|
| note-skill | platform | C3、C5、P1 |
| research-skill | platform | `/api/plugins/research-skill` 的 scheme 仍为 `loop` |
| testgen-skill | testgen | scheme 仍为 `loop`，且 I2 读不到它的文件记忆标记 |
| novel-writer-skill | novel | scheme 仍为 `loop` |
| ops-deploy-skill | ops | scheme 仍为 `action` |
| weather-skill | platform | scheme 仍为 `langchain` |

不在本轮为每个 loop 技能重放完整生成。它们的对外入参出参没有改。

## 6. 一批结束时怎么勾

| 批次 | 至少跑过 |
|------|----------|
| 1 | C1–C7、I5、I6、第 5 节的加载检查 |
| 2 | 上一批 + I1、I2、I3、M1、M2，以及 `selftest-memory.js` |
| 3 | 上一批 + P1、P2。有模型则加 P4–P6 |
| 4 | 上一批 + P3 |
| 5 | 上一批 + I4、M3。确认未开知识库工具的 chat 响应字段与 P1 相同 |
| 6 | 上表全部自动项进仓库；手动项填下面的记录 |
